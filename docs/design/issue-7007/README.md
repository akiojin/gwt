## 画面構成の原則

- **1.** プロジェクトはブラウザのタブで開く。プロジェクトごとに独立した URL ページを複数タブで並べる現行の使い方を土台とし、アプリ内タブは採用しない。
- **2.** アプリの起点は開始画面（現行 Hub）。ただし開始画面の中身はプロジェクトのランチャーではなく、端末 PM との会話の場所とする（開いたら PM が様子を話しかけ、返事を書けば仕事が進む体験）。プロジェクト一覧は脇に小さく置く。
- **3.** 複数プロジェクトの横断統一はしない。1画面＝1文脈。横断に置くのは判断待ちと件数レベルの要約だけとする。
- **4.** Your PM の独立ページは廃止する。PM の表示は開始画面に集約し、判断は各プロジェクトのページでも完結できる形にする。
- **5.** 開始画面の右側には「プロジェクトの今」（注意が要るプロジェクトの作業状況）を置く。タスク数・Issue 数はプロジェクトページに入らなくても、開始画面の要約と PM への質問で足りるようにする。
- **6.** プロジェクト数の両端を設計に含める。無い状態では PM が案内役になり、GitHub から取り込む／フォルダを開くの入口を出す。多い状態（20件規模）では注意が要るものだけを厚く見せ、静かなものは畳む。全件一覧は検索つきで別に持つ。
- **7.** 全ページ共通のヘッダーとフッターを持つ。ヘッダー右には PM の状態（アバター＋判断待ち件数）、エージェント台帳への入口、設定への入口を常時同じ並びで置く。フッターにはバージョンと稼働状態のような静かな情報だけを置く。

## PM とエージェントのモデル

- **8.** PM も Agent の一種である。用語は、ツール／プロバイダ（Codex・Claude Code 等）を「Tool」、名前を持ってタスクを担当する実体（メンバーと PM）を「Agent」と分ける。
- **9.** 「PM を務める」は、エージェントの設定に置くチェックボックスの属性とする。意味は「現在の PM」の指名ではなく「PM になることができる」という可能の印である。PM の実行設定（使うツール／モデル）は、そのエージェント自身の設定として持つ。PM の振る舞い設定（知らせ方等）は設定の「あなたの PM」に残すが、これは「PM を務めるエージェントの振る舞い設定」である。
- **10.** エージェントの利用優先度は台帳の並び順（上から順）である。PM の選出もこの例外ではなく、PM 可能なエージェントの中で並び順が最も上で適格な1人が PM を務める。
- **11.** レート制限への対処は、エージェントの追加と並び順で吸収する。PM 専用の「予備」機構は作らない。現在の PM が適格でなくなれば、次の順位の PM 可能なエージェントが引き継ぐ。PM の会話・記憶・判断待ちは gwt 側に保持されるため、務めるエージェントが替わっても PM の文脈は続く。
- **12.** PM には名前とアバターを持たせる（モックでは仮名「ツムギ」）。狙いは「Muse と話すのと同じ感覚で PM とも話せる」体験である。プロジェクトページの「相談」も同じ端末 PM であり、文脈が違うだけで会話は分裂しない。

## その他

- **13.** Custom Agents と Backends は廃止する（#7026 と連動）。
- **14.** モックの作法：モックは現行画面の再現ではなく体験の設計として作る。画面内に設計意図の説明文は置かず、ラベル・状態の一言・PM の発言・空状態の案内のみを置く（設計の記録は本書と #7007 コメントに集約する）。モックの UI 文言は日本語とする（製品 UI の英語方針とは別）。
