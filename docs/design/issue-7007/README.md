## 画面構成の原則

- **1.** プロジェクトはブラウザのタブで開く。プロジェクトごとに独立した URL ページを複数タブで並べる現行の使い方を土台とし、アプリ内タブは採用しない。
- **2.** アプリの起点は開始画面（現行 Hub）。ただし開始画面の中身はプロジェクトのランチャーではなく、端末 PM との会話の場所とする（開いたら PM が様子を話しかけ、返事を書けば仕事が進む体験）。プロジェクト一覧は脇に小さく置く。
- **3.** 複数プロジェクトの横断統一はしない。1画面＝1文脈。横断に置くのは判断待ちと件数レベルの要約だけとする。
- **4.** Your PM の独立ページは廃止する。PM の表示は開始画面に集約し、判断は各プロジェクトのページでも完結できる形にする。
- **5.** 開始画面にプロジェクトの内容は表示しない（2026-11-18 オーナー決定で改定。旧案の右側「プロジェクトの今」は置かない）。開始画面は PM とのやり取りがメインであり、プロジェクトの作業状況・タスク数・Issue 数などの内容は各プロジェクトのページで見る。脇のプロジェクト一覧は名前だけの導線に留め、状況や件数などの内容は付けない。
- **6.** プロジェクト数の両端を設計に含める。無い状態では PM が案内役になり、GitHub から取り込む／フォルダを開くの入口を出す。多い状態（20件規模）でも開始画面の一覧は名前だけの導線のまま（項目5）とし、全件一覧は検索つきで別に持つ。
- **7.** 全ページ共通のヘッダーとフッターを持つ。ヘッダー右には PM の状態（アバター＋判断待ち件数）、エージェント台帳への入口、設定への入口を常時同じ並びで置く。フッターにはバージョンと稼働状態のような静かな情報だけを置く。

## PM とエージェントのモデル

- **8.** PM も Agent の一種である。用語は、ツール／プロバイダ（Codex・Claude Code 等）を「Tool」、名前を持ってタスクを担当する実体（メンバーと PM）を「Agent」と分ける。
- **9.** 「PM を務める」は、エージェントの設定に置くチェックボックスの属性とする。意味は「現在の PM」の指名ではなく「PM になることができる」という可能の印である。PM の実行設定（使うツール／モデル）は、そのエージェント自身の設定として持つ。PM の振る舞い設定（知らせ方等）は設定の「あなたの PM」に残すが、これは「PM を務めるエージェントの振る舞い設定」である。
- **10.** エージェントの利用優先度は台帳の並び順（上から順）である。PM の選出もこの例外ではなく、PM 可能なエージェントの中で並び順が最も上で適格な1人が PM を務める。
- **11.** レート制限への対処は、エージェントの追加と並び順で吸収する。PM 専用の「予備」機構は作らない。現在の PM が適格でなくなれば、次の順位の PM 可能なエージェントが引き継ぐ。PM の会話・記憶・判断待ちは gwt 側に保持されるため、務めるエージェントが替わっても PM の文脈は続く。
- **12.** PM には名前とアバターを持たせる（モックでは仮名「ツムギ」）。狙いは「Muse と話すのと同じ感覚で PM とも話せる」体験である。プロジェクトページの「相談」も同じ端末 PM であり、文脈が違うだけで会話は分裂しない。

## アバター（2026-11-14 オーナー指示、2026-11-17 本書へ反映）

- **17.** アバターは PM だけでなく、エージェント台帳に載る全 Agent が持てることとする。開始画面の PM 要約ブロック、共通ヘッダーの PM 状態、各プロジェクト画面のエージェント表示など、アバターが表示される箇所はすべてこの仕組みに乗る。項目12（PM には名前とアバターを持たせる）は本節に包含される。
- **18.** アバターは Agent 側の属性である（#7278 の Agent／Tool 分離と整合させる）。名前・役割・PM 適格と並んで Agent の人格に属し、Tool インスタンス（アカウント単位の実体）には紐づけない。したがって、セッションへの Tool 割当が変わってもアバターは変わらず、同じ Agent はどの画面・どのセッションでも同じアバターで表示される。
- **19.** アバターはアニメーションする表示に対応する。状態に応じた動き（例：稼働中／待機中／詰まり）を含めるか、その粒度は実装スライス T-019 で詰めるが、静止画前提の表示部品にはしない（アニメーション資産を設定できるデータ形式と表示経路を最初から確保する）。
- **20.** アバターの設定方法は2通りとする。(a) プリセットを複数用意し、その中から選択できる。(b) 自分の画像をアップロードして設定できる。未設定の Agent には既定のプリセット（イニシャル表示等）を割り当て、表示が欠ける状態を作らない。設定はエージェント台帳／エージェント設定から行い、全表示箇所へ即時反映される。

## 実装スライス（アバター、T-017 以降）

残りスライス T-015（共有ステータスバー）・T-016（E2E・回帰確認）の後段に、アバター対応を次のスライスで組み込む。各スライスは単独で配信可能な大きさに切る。

- **T-017：Agent アバター属性の基盤とプリセット選択**
  - Agent のデータにアバター設定（種別：プリセット／アップロード／既定、プリセット ID）を持たせ、台帳・エージェント設定でプリセットを複数から選択できるようにする。表示は開始画面の PM 要約・共通ヘッダー・プロジェクト画面のエージェント表示で共通部品を使う。
  - 受け入れ条件：(1) 台帳の全 Agent にアバターが表示される（未設定は既定表示）。(2) プリセットを変更すると全表示箇所へ即時反映される。(3) Tool 割当を変えてもアバターが変わらない。(4) 既存の Agent データ（アバター未設定）でも表示が壊れない。
- **T-018：画像アップロードによるアバター設定**
  - エージェント設定から自分の画像をアップロードしてアバターに設定できるようにする。保存先・形式変換（正方形切り抜き等）・上限サイズを定め、プリセットへの切り戻しも可能にする。
  - 受け入れ条件：(1) アップロードした画像が全表示箇所に反映される。(2) 非対応形式・上限超過はエラーとして表示され、既存設定を壊さない。(3) プリセット選択へいつでも戻せる。(4) アップロード画像は端末ローカルに保存され、外部へ送信されない。
- **T-019：アバターのアニメーション対応**
  - アバター表示部品をアニメーション可能な形式（アニメーション資産または状態に応じた動き）に対応させる。動きの粒度（常時アニメーション／状態連動）は本スライスの設計で確定し、過剰な動きで作業表示を妨げない配慮（停止設定を含む）を入れる。
  - 受け入れ条件：(1) プリセット・アップロードの双方でアニメーション表示が可能な経路がある。(2) 状態連動を行う場合は稼働中／待機中／詰まりで表示が区別できる。(3) アニメーションを止める設定があり、全表示箇所に効く。(4) アニメーション有無でレイアウトが崩れない。
- **T-020：アバター表示の E2E・回帰確認**
  - T-017〜T-019 の表示を実機（headed）で確認する回帰スライス。dark／light 両テーマ、全表示箇所（開始画面・ヘッダー・プロジェクト画面・台帳）での表示と設定変更の反映を検証する。
  - 受け入れ条件：(1) 全表示箇所でアバターが表示され、欠け・崩れがない。(2) 設定変更（プリセット／アップロード／アニメーション停止）が全箇所へ反映される。(3) console／page error が無い。

## 実装スライス（全画面刷新 v3、T-021 以降）

2026-11-18 の決定群（項目21〜31）とモック v3 に合わせて、残りスライスを切り直す（2026-11-18 オーナー決定「v3 の実装スライスも sub-issue で切る（既存Tの見直し込み）」）。各スライスは #7007 の sub-issue として管理する。

既存スライスの扱い：

- **T-016（E2E・回帰確認、sub-issue #7634）**：対象範囲を T-001〜T-015（タスク中心の基礎面）の回帰として明確化する。v3 で追加される画面群の総合確認は T-036 が担う。
- **T-017〜T-020（アバター、sub-issue #7635〜#7638）**：定義を維持する。ただし表示箇所の文言は v3 に合わせ、開始画面については「PM 要約」ではなく開始画面の PM 表示（会話相手とヘッダーの PM 状態）を指すものとする。
- **番号衝突の reconcile**：#7007 本文のタスク表で T-017〜T-020 に割り当てられていた最終工程（検証記録の取得／利用者評価／README 反映／Ready PR・auto-merge 配信）は、設計正本のアバター T-017〜T-020 を正として、本節の T-037〜T-040 に置き直す。

新規スライス：

- **T-021：開始画面の会話化**
  - 開始画面を端末 PM との会話の場所として実装する（原則2・5・6、決定22）。プロジェクト一覧は名前だけの導線とし、プロジェクトの内容・件数は出さない。判断待ちは会話の中の判断カード（おすすめ・理由・影響範囲つき）で提示し、その場で決定できる。プロジェクトが無い状態では PM が案内役になり、取り込み／フォルダを開く入口を出す。
  - 受け入れ条件：(1) 開始画面の主体が PM との会話であり、プロジェクトの作業状況・件数が表示されない。(2) 判断カードから決定でき、結果が対象プロジェクトへ反映される。(3) プロジェクト無し・20件規模の両端で導線が破綻しない。
- **T-022：PM ビューの廃止と相談への一本化**
  - PM ビュー（8タブ）を廃止し、PM との会話は開始画面と各プロジェクトの「相談」に一本化する（決定29）。Log タブ（Notifications の再描画）は置かない。PM の生出力は作業側に寄せ、PM を含む全エージェントのツール出力をターミナル表示で開ける導線を作業画面に置く（基本はチャット、実物はターミナル）。
  - 受け入れ条件：(1) PM ビューのタブが存在せず、会話の場所が開始画面と相談だけになる。(2) PM のセッション出力を作業画面からターミナル表示で確認できる。(3) Notifications の内容が PM ビュー経由の再描画なしに直接見られる。
- **T-023：判断表示の一本化**
  - 判断の表示と回答の経路を、判断待ち画面と会話内カードに一本化する（決定22・29）。Reports と Chat に重複描画されていた decision レポート表示を撤去し、判断データ（PM レポートの decision）の描画箇所をこの2つに限る。空操作だった「Later」は、実体のある扱い（下書きとして残す等）に改めるか撤去する。
  - 受け入れ条件：(1) 未回答の判断が判断待ち画面と会話内カードにだけ現れる。(2) どちらの経路で回答しても同じ判断が解決済みになる。(3) 判断件数（ヘッダー・ステータスバー）が実態と一致する。
- **T-024：報告の掲示板統合**
  - PM の報告の置き場を掲示板に統合する（決定29）。PM レポートは掲示板の投稿として残り、Q&A と重要な進捗・決定が必ず掲示板に残る形にする。未解決の詰まりの索引（fold）は原則16のとおり掲示板に維持する。Board と PM レポートで別々だったストアは一本化するか、掲示板側を正本として PM レポートをその生成経路に改める。
  - 受け入れ条件：(1) PM の報告が掲示板で時系列に追える。(2) 報告が「載ったり載らなかったり」しない（生成された報告は必ず掲示板に現れる）。(3) 判断の報告は T-023 の判断表示と矛盾しない。
- **T-025：タスク画面**
  - プロジェクト内にタスクの独立画面を実装する（決定23）。タスク一覧→タスク詳細→配下の Issue の階層で見せ、タスク詳細から配下 Issue を開ける。「今日の完了数」は実数化してタスク画面に出す（決定24。データソースを持たない "Unknown" 表示は廃止する）。
  - 受け入れ条件：(1) タスク一覧・詳細・配下 Issue の遷移が成立する。(2) 今日の完了数が実データから計算され、開始画面には出ない。(3) タスクが無い状態では空状態の案内が出る。
- **T-026：タスクの自動記録**
  - 会話で頼まれたこと・決まったことを PM がタスクとして自動で記録する仕組みを実装する（決定23）。現行の手動 capture（PM が会話ターンを選んで記録する運用）は前提にせず、記録の漏れが起きない経路にする。記録されたタスクは T-025 のタスク画面に現れる。
  - 受け入れ条件：(1) 相談で依頼・決定した内容が、人の追加操作なしにタスクとして残る。(2) 記録されたタスクから元の会話へ辿れる。(3) 明示的に「タスクにしない」扱いもできる。
- **T-027：タスク／Issue 階層の GitHub sub-issue 式化**
  - 階層を GitHub sub-issue 式にする（決定31）。Issue の下に子 Issue をぶら下げられ、子の状態が親へ集計されて進捗として表示される。タスクと Issue の関係も同じ階層の仕組みに乗せる。
  - 受け入れ条件：(1) Issue に子 Issue を追加・解除できる。(2) 親の進捗が子の完了状況から自動で集計される。(3) 課題画面とタスク詳細の双方で階層と進捗が一貫して見える。
- **T-028：エージェント台帳の独立画面化**
  - エージェント台帳をアプリ設定から取り出し、全ページ共通ヘッダーから開く独立画面にする（決定25）。台帳が持つのは名前・アバター・役割・PM 適格・並び順（優先度）＋特性（T-029）のみとし、担当履歴・担当予定は置かない。アプリ設定側には台帳への導線だけを残す。
  - 受け入れ条件：(1) ヘッダーから台帳の独立画面へ遷移できる。(2) アプリ設定内に台帳の編集 UI が残っていない。(3) 並び順の変更が PM 選出と利用優先度に反映される。
- **T-029：エージェント特性の導入**
  - エージェントの特性（推論レベル・速度・性格＝開発や調査でどこを重点に置くか）を Agent の固定属性として導入する（決定26）。特性は起動計画で上書きしない。あわせて台帳の「使える Tool 種別」を撤去し、Tool は起動時に Issue 側の計画と Tool プールの状態で決まる形にする（決定27。#7278 の設計変更と整合させる）。
  - 受け入れ条件：(1) 台帳で特性を表示・設定でき、セッション起動時にその特性どおりに動く。(2) 起動計画側に特性を上書きする項目が無い。(3) 台帳に Tool 種別の設定が無く、Tool の決定が計画とプール状態から行われる。
- **T-030：ツール画面**
  - Tool インスタンスのプール（種別・使用率・リセット時刻・制限状態・サインイン状態）を、ヘッダーから開く独立画面として実装する（決定28）。プロバイダ使用量の表示はこの画面に集約し、アプリ設定からは取り除く（導線のみ残す）。
  - 受け入れ条件：(1) ヘッダーからツール画面へ遷移でき、全インスタンスの状態が見える。(2) 使用率・リセット・制限状態が実態と一致する。(3) 使用量の表示箇所がツール画面だけになる。
- **T-031：担当履歴・担当予定（プロジェクトのエージェント画面）**
  - プロジェクトのエージェント画面に、担当履歴（Issue × Tool × モデル／推論 × 結果）と担当予定を置く（決定25）。履歴は PM の行を含め、使ったモデル／推論が欠けない形で記録・表示する。台帳には置かない。
  - 受け入れ条件：(1) エージェントごとに担当した Issue と Tool・モデル／推論・結果が遡れる。(2) 担当予定が実際の割当計画と一致して表示される。(3) 台帳側に履歴・予定の表示が無い。
- **T-032：Logs の刷新**
  - Logs を作り替える（決定30）。アプリの構造化ログを唯一のログ面とし、PM ビューの Log タブ廃止（T-022）と合わせて、ログの置き場をここに一本化する。
  - 受け入れ条件：(1) 構造化ログが検索・絞り込みつきで追える。(2) PM の実行記録を辿る経路が Logs か作業画面のターミナル表示のどちらかに一本化されている。(3) 旧 Log タブ相当の再描画が残っていない。
- **T-033：Profile の刷新**
  - Profile を作り替える（決定30）。端末全体のプロファイルとして、他の画面（台帳・ツール・設定）と文脈が重ならない形に整理する。
  - 受け入れ条件：(1) Profile が独立画面として成立し、表示項目が実態と一致する。(2) 台帳・ツール・設定との二重配置が無い。
- **T-034：起動ウィザードの刷新**
  - 起動ウィザードを作り替える（決定30）。初回セットアップは新しいモデル（エージェント台帳と Tool プール）に合わせ、最低1つの Tool インスタンスの登録とサインインが済むまで進めない必須セットアップ（#7278 の PM 例外）を含む。
  - 受け入れ条件：(1) 初回起動で台帳と Tool プールの初期設定が完結する。(2) Tool 未登録では先へ進めず、その理由が表示される。(3) 既存ユーザーの起動を妨げない。
- **T-035：コマンドパレットの刷新**
  - コマンドパレットを作り替える（決定30）。新しい行き先（タスク画面・台帳・ツール画面を含む全画面）へ遷移でき、画面構成の原則（1画面＝1文脈）と矛盾しない検索・実行の範囲にする。

## 全画面刷新の追加決定（2026-11-18 設計インタビュー）

2026-11-18 の設計インタビュー（選択式）で確定した決定を記録する。モック v3 は本節の決定に合わせて作り替える。

- **21.** 進め方：モック v3 を作りながら、画面ごとに選択式で判断を聞いて整理する（2026-11-18 決定）。
- **22.** 開始画面の判断待ち：会話の中の判断カードで、その場で決められるようにする。
- **23.** タスク：プロジェクト内の独立画面とする（タスク一覧→タスク詳細→配下の Issue）。タスクの記録は自動とする（会話で頼まれたこと・決まったことを PM がタスク化して残す）。現行の手動 capture 運用は前提にしない。
- **24.** 「今日の完了数」：実数化してタスク画面に出す。開始画面には出さない（項目5と整合）。現行の未実装 "Unknown" 枠は廃止する。
- **25.** エージェント台帳：独立画面とし、全ページ共通ヘッダーから開く（項目7の入口と対応）。台帳が持つのは名前・アバター・役割・PM 適格・並び順（優先度）＋特性（項目26）のみとする。担当履歴・担当予定は台帳に置かず、プロジェクトのエージェント画面側に置く。
- **26.** エージェントの特性：推論レベル・速度（Fast／Ultrafast 等）・性格（開発や調査でどこを重点に置くか）を特性として持つ。特性はエージェント固定とし、起動計画で上書きしない。
- **27.** 使える Tool 種別：エージェント台帳には持たない。Tool は起動時に、Issue 側の計画と Tool プールの状態で決まる。これは #7278 の設計（Agent 側に Tool 種別・利用可能種別・優先度を持つ）からの変更である。
- **28.** ツール画面：Tool インスタンスのプール（使用率・リセット・制限状態の管理）は独立画面とし、ヘッダーから開く。アプリ設定には入れない。プロバイダ使用量の表示はツール画面に寄せる。
- **29.** PM の一本化：PM ビュー（8タブ）は廃止し、会話は相談に一本化する。判断は判断待ち画面と会話内カードへ、報告は掲示板へ統合し（PM の報告は掲示板に残る形）、進捗は作業・課題画面の実物を正本とする。Log タブ（Notifications の再描画）は廃止する。PM の生出力は作業側に寄せ、基本はチャットとしつつ、PM を含む全エージェントのツール出力をターミナル表示で見られるようにする。
- **30.** 刷新の範囲：Logs・Profile・プロバイダ使用量・起動ウィザード・コマンドパレットも作り替えに含める。
- **31.** 階層は GitHub sub-issue 式とする：タスク→Issue の2層に限らず、Issue の下にも子 Issue をぶら下げられる。子の完了は親へ集計され、進捗として見える（GitHub の sub-issues 進捗バーと同型の見え方）。タスク（複数 Issue を束ねるテーマ、項目23）も同じ集計の仕組みで扱い、タスク詳細・課題詳細・課題一覧の進捗表示は同じ様式に揃える。課題詳細には子課題の一覧・進捗集計・子課題の追加導線と、親（タスクまたは課題）への導線を置く。
- **32.** 開始画面の上部にプロジェクトのタブを表示する：タブはプロジェクト名のみとし、件数・要約・バッジは出さない（項目5の「開始画面にプロジェクトの内容を表示しない」と両立する）。先頭は開始画面自体（ホーム）のタブとし、各プロジェクトのタブからそのプロジェクトのページへ遷移する。脇の名前だけのプロジェクト一覧（項目6）は残す。
- **33.** 表示名の注記：「エージェント台帳」（項目25）の導線ラベル（上部タブ・ヘッダーの入口・コマンドパレット等の行き先名）は「エージェント」と呼ぶ。画面の中身（台帳としての属性・特性の一覧）は変えない。
- **31.** タスク／Issue の階層は GitHub sub-issue 式とする（2026-11-18 決定）：タスク→Issue の2層に固定せず、Issue の下にも子 Issue をぶら下げられるようにし、子の完了は親へ集計して進捗として見せる。
