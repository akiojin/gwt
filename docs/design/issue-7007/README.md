## 画面構成の原則

- **1.** プロジェクトはブラウザのタブで開く。プロジェクトごとに独立した URL ページを複数タブで並べる現行の使い方を土台とし、アプリ内タブは採用しない。
- **2.** アプリの起点はホーム（現行 Hub）。ただしホームの中身はプロジェクトのランチャーではなく、端末 PM との会話の場所とする（開いたら PM が様子を話しかけ、返事を書けば仕事が進む体験）。プロジェクト一覧は脇に小さく置く。
- **3.** 複数プロジェクトの横断統一はしない。1画面＝1文脈。横断に置くのは判断待ちと件数レベルの要約だけとする。
- **4.** Your PM の独立ページは廃止する。PM の表示はホームに集約し、判断は各プロジェクトのページでも完結できる形にする。
- **5.** ホームにプロジェクトの内容は表示しない（2026-11-18 オーナー決定で改定。旧案の右側「プロジェクトの今」は置かない）。ホームは PM とのやり取りがメインであり、プロジェクトの作業状況・テーマ数・Issue 数などの内容は各プロジェクトのページで見る。脇のプロジェクト一覧は名前だけの導線に留め、状況や件数などの内容は付けない。（項目46・50で置き換え：ホームは PM との会話のみとし、プロジェクトの内容・状態は出さない）
- **6.** プロジェクト数の両端を設計に含める。無い状態では PM が案内役になり、GitHub から取り込む／フォルダを開くの入口を出す。多い状態（20件規模）でもホームの一覧は名前だけの導線のまま（項目5）とし、全件一覧は検索つきで別に持つ。（項目46・49で置き換え：プロジェクトが多い状態の入口はヘッダーのプロジェクトタブから開く一覧画面とし、ホームの一覧は名前だけの導線に留める）
- **7.** 全ページ共通のヘッダーとフッターを持つ。ヘッダー右には PM の状態（アバター＋判断待ち件数）、エージェントへの入口、設定への入口を常時同じ並びで置く。フッターにはバージョンと稼働状態のような静かな情報だけを置く。（項目155で置き換え：フッターはバージョンと PM 名だけとし、稼働状態・判断待ち件数は置かない）

## PM とエージェントのモデル

- **8.** PM も Agent の一種である。用語は、ツール／プロバイダ（Codex・Claude Code 等）を「Tool」、名前を持ってタスクを担当する実体（メンバーと PM）を「Agent」と分ける。
- **9.** 「PM を務める」は、エージェントの設定に置くチェックボックスの属性とする。意味は「現在の PM」の指名ではなく「PM になることができる」という可能の印である。PM の実行設定（使うツール／モデル）は、そのエージェント自身の設定として持つ。PM の振る舞い設定（知らせ方等）は設定の「あなたの PM」に残すが、これは「PM を務めるエージェントの振る舞い設定」である。（「PM を務める」チェックは項目44で廃止し、PM の決め方は項目100で置き換え）
- **10.** エージェントの利用優先度は台帳の並び順（上から順）である。PM の選出もこの例外ではなく、PM 可能なエージェントの中で並び順が最も上で適格な1人が PM を務める。（PM の選出に関する部分は項目100で置き換え）
- **11.** レート制限への対処は、エージェントの追加と並び順で吸収する。PM 専用の「予備」機構は作らない。PM が替わるのは、ユーザーが割り当て直したときだけであり、自動引き継ぎはしない（項目100で置き換え）。PM の会話・記憶・判断待ちは gwt 側に保持されるため、務めるエージェントが替わっても PM の文脈は続く。
- **12.** PM には名前とアバターを持たせる（モックでは仮名「ツムギ」）。狙いは「Muse と話すのと同じ感覚で PM とも話せる」体験である。プロジェクトページの「相談」も同じ端末 PM であり、文脈が違うだけで会話は分裂しない。（項目64で置き換え：プロジェクト側に相談タブ・会話は置かず、PM とのやり取りはホームに一本化する）

## アバター（2026-11-14 オーナー指示、2026-11-17 本書へ反映）

- **17.** アバターは PM だけでなく、エージェント台帳に載る全 Agent が持てることとする。ホームの PM 要約ブロック、共通ヘッダーの PM 状態、各プロジェクト画面のエージェント表示など、アバターが表示される箇所はすべてこの仕組みに乗る。項目12（PM には名前とアバターを持たせる）は本節に包含される。
- **18.** アバターは Agent 側の属性である（#7278 の Agent／Tool 分離と整合させる）。名前・役割・PM 適格と並んで Agent の人格に属し、Tool インスタンス（アカウント単位の実体）には紐づけない。したがって、セッションへの Tool 割当が変わってもアバターは変わらず、同じ Agent はどの画面・どのセッションでも同じアバターで表示される。（項目41・44で置き換え：エージェントは役割と PM 適格を持たず、PM は指名制とする）
- **19.** アバターはアニメーションする表示に対応する。状態に応じた動き（例：稼働中／待機中／詰まり）を含めるか、その粒度は実装スライス T-019 で詰めるが、静止画前提の表示部品にはしない（アニメーション資産を設定できるデータ形式と表示経路を最初から確保する）。（2026-11-18 本人決定で置き換え：アバターの動き（アニメーション）は廃止し、静止画のみとする。項目111を参照。実装スライス T-019 はクローズした。）
- **20.** アバターの設定方法は2通りとする。(a) プリセットを複数用意し、その中から選択できる。(b) 自分の画像をアップロードして設定できる。未設定の Agent には既定のプリセット（イニシャル表示等）を割り当て、表示が欠ける状態を作らない。設定はエージェント／エージェント設定から行い、全表示箇所へ即時反映される。

## 実装スライス（アバター、T-017 以降）

残りスライス T-015（共有ステータスバー）・T-016（E2E・回帰確認）の後段に、アバター対応を次のスライスで組み込む。各スライスは単独で配信可能な大きさに切る。

- **T-017：Agent アバター属性の基盤とプリセット選択**
  - Agent のデータにアバター設定（種別：プリセット／アップロード／既定、プリセット ID）を持たせ、台帳・エージェント設定でプリセットを複数から選択できるようにする。表示はホームの PM 要約・共通ヘッダー・プロジェクト画面のエージェント表示で共通部品を使う。
  - 受け入れ条件：(1) 台帳の全 Agent にアバターが表示される（未設定は既定表示）。(2) プリセットを変更すると全表示箇所へ即時反映される。(3) Tool 割当を変えてもアバターが変わらない。(4) 既存の Agent データ（アバター未設定）でも表示が壊れない。
- **T-018：画像アップロードによるアバター設定**
  - エージェント設定から自分の画像をアップロードしてアバターに設定できるようにする。保存先・形式変換（正方形切り抜き等）・上限サイズを定め、プリセットへの切り戻しも可能にする。
  - 受け入れ条件：(1) アップロードした画像が全表示箇所に反映される。(2) 非対応形式・上限超過はエラーとして表示され、既存設定を壊さない。(3) プリセット選択へいつでも戻せる。(4) アップロード画像は端末ローカルに保存され、外部へ送信されない。
  - 決定（#7636）：保存先は端末ローカルの Agent 台帳（アバター設定に PNG の data URL として保持し、外部へ送信しない）。受け付ける元画像は PNG / JPEG / WebP / GIF で 5 MB まで。GUI が中央の正方形を切り抜いて 128px 四方の PNG に変換し、台帳は PNG 以外と 64 KiB 超を拒否する。プリセットまたは既定を選ぶと画像は破棄される。
- **T-019：アバターのアニメーション対応**（2026-11-18：項目111の決定により廃止。sub-issue #7637 はクローズした）
  - アバター表示部品をアニメーション可能な形式（アニメーション資産または状態に応じた動き）に対応させる。動きの粒度（常時アニメーション／状態連動）は本スライスの設計で確定し、過剰な動きで作業表示を妨げない配慮（停止設定を含む）を入れる。
  - 受け入れ条件：(1) プリセット・アップロードの双方でアニメーション表示が可能な経路がある。(2) 状態連動を行う場合は稼働中／待機中／詰まりで表示が区別できる。(3) アニメーションを止める設定があり、全表示箇所に効く。(4) アニメーション有無でレイアウトが崩れない。
- **T-020：アバター表示の E2E・回帰確認**
  - T-017〜T-019 の表示を実機（headed）で確認する回帰スライス。dark／light 両テーマ、全表示箇所（ホーム・ヘッダー・プロジェクト画面・台帳）での表示と設定変更の反映を検証する。
  - 受け入れ条件：(1) 全表示箇所でアバターが表示され、欠け・崩れがない。(2) 設定変更（プリセット／アップロード）が全箇所へ反映される。(3) console／page error が無い。

新規スライス：

- **T-021：ホームの会話化**（2026-11-19 前提変更：プロジェクト一覧はホームの脇ではなく、ヘッダーのプロジェクトタブから開く一覧画面とする（項目46・50））
  - ホームを端末 PM との会話の場所として実装する（原則2・5・6、決定22）。プロジェクト一覧は名前だけの導線とし、プロジェクトの内容・件数は出さない。判断待ちは会話の中の PM の発言（出来事→問いかけ→おすすめとその理由→影響を文章で含む。項目226の会話形式）として提示し、その場で決定できる。プロジェクトが無い状態では PM が案内役になり、取り込み／フォルダを開く入口を出す。
  - 受け入れ条件：(1) ホームの主体が PM との会話であり、プロジェクトの作業状況・件数が表示されない。(2) 会話の中の発言から決定でき、結果が対象プロジェクトへ反映される。(3) プロジェクト無し・20件規模の両端で導線が破綻しない。
- **T-022：PM ビューの廃止と相談への一本化**（2026-11-19 前提変更：PM との会話はホームに一本化し、プロジェクト側に「相談」は置かない（項目64）。PM の出力は課題とエージェントの画面から開く（項目137））
  - PM ビュー（8タブ）を廃止し、PM との会話はホームと各プロジェクトの「相談」に一本化する（決定29）。Log タブ（Notifications の再描画）は置かない。PM の生出力は作業側に寄せ、PM を含む全エージェントのツール出力をターミナル表示で開ける導線を作業画面に置く（基本はチャット、実物はターミナル）。
  - 受け入れ条件：(1) PM ビューのタブが存在せず、会話の場所がホームと相談だけになる。(2) PM のセッション出力を作業画面からターミナル表示で確認できる。(3) Notifications の内容が PM ビュー経由の再描画なしに直接見られる。
- **T-023：判断表示の一本化**
  - 判断の表示と回答の経路を、判断待ち画面（キュー側）と会話の中の発言に一本化する（決定22・29、項目226）。Reports と Chat に重複描画されていた decision レポート表示を撤去し、判断データ（PM レポートの decision）の描画箇所をこの2つに限る。空操作だった「Later」は、実体のある扱い（下書きとして残す等）に改めるか撤去する。
  - 受け入れ条件：(1) 未回答の判断が判断待ち画面と会話の中の発言にだけ現れる。(2) どちらの経路で回答しても同じ判断が解決済みになる。(3) 判断件数（ヘッダー・ステータスバー）が実態と一致する。
- **T-024：報告の掲示板統合**
  - PM の報告の置き場を掲示板に統合する（決定29）。PM レポートは掲示板の投稿として残り、Q&A と重要な進捗・決定が必ず掲示板に残る形にする。未解決の詰まりの索引（fold）は原則16のとおり掲示板に維持する。（2026-11-19 項目152で前提変更：掲示板は記録専用・スレッド形式とし、状態管理の仕組みは持たない。実体はプロジェクトごとに選択する。fold は掲示板に維持せず、課題一覧の状態＋理由へ移す。本スライスの「報告が掲示板に残る」部分は、記録として残る形で維持する。）Board と PM レポートで別々だったストアは一本化するか、掲示板側を正本として PM レポートをその生成経路に改める。
  - 受け入れ条件：(1) PM の報告が掲示板で時系列に追える。(2) 報告が「載ったり載らなかったり」しない（生成された報告は必ず掲示板に現れる）。(3) 判断の報告は T-023 の判断表示と矛盾しない。
- **T-025：テーマ画面**
  - プロジェクト内にテーマの独立画面を実装する（決定23）。テーマ一覧→テーマ詳細→配下の Issue の階層で見せ、テーマ詳細から配下 Issue を開ける。「今日の完了数」は実数化してテーマ画面に出す（決定24。データソースを持たない "Unknown" 表示は廃止する）。
  - 受け入れ条件：(1) テーマ一覧・詳細・配下 Issue の遷移が成立する。(2) 今日の完了数が実データから計算され、ホームには出ない。(3) テーマが無い状態では空状態の案内が出る。
- **T-026：テーマの自動記録**
  - 会話で頼まれたこと・決まったことを PM がテーマとして自動で記録する仕組みを実装する（決定23）。現行の手動 capture（PM が会話ターンを選んで記録する運用）は前提にせず、記録の漏れが起きない経路にする。記録されたテーマは T-025 のテーマ画面に現れる。
  - 受け入れ条件：(1) 相談で依頼・決定した内容が、人の追加操作なしにテーマとして残る。(2) 記録されたテーマから元の会話へ辿れる。(3) 明示的に「テーマにしない」扱いもできる。
  - 実装の形（Issue #7644、2026-11-23）：ホームの会話の人のターンごとに、PM が `pm.theme.record` で判断を1つ記録する（新規テーマは `gwt-theme` ラベル付きの GitHub Issue の作成、既存テーマへの追記はコメント、「テーマにしない」と依頼なしは GitHub に書かずに判断だけを残す）。記録は最新の人のメッセージに紐付き、Issue 本文とコメントに会話の出所（PM のセッションとメッセージ）を残す。判断が無いまま PM が止まろうとすると、Stop ゲートが1ターンに1回催促する。テーマ画面は `gwt-theme` ラベル付きの Issue を配下が無くてもテーマとして表示し、テーマ詳細の「記録のもと」から元のメッセージを PM の会話で開ける。
- **T-027：テーマ／Issue 階層の GitHub sub-issue 式化**（2026-11-19 前提変更：階層はテーマ→課題の親子のみとし、課題同士の親子は GitHub の sub-issue ではなく課題の本文内の項目で管理する（項目173）。受け入れ条件(1)の「子 Issue を追加・解除できる」は置き換える）
  - 階層を GitHub sub-issue 式にする（決定31）。Issue の下に子 Issue をぶら下げられ、子の状態が親へ集計されて進捗として表示される。テーマと Issue の関係も同じ階層の仕組みに乗せる。
  - 受け入れ条件：(1) Issue に子 Issue を追加・解除できる。(2) 親の進捗が子の完了状況から自動で集計される。(3) 課題画面とテーマ詳細の双方で階層と進捗が一貫して見える。
- **T-028：エージェント台帳の独立画面化**（2026-11-19 前提変更：台帳の属性は名前・アバター・並び順＋特性のみとし、役割・PM 適格は持たない。PM は指名制で、並び順は PM の選出に使わない（項目41・44・100））
  - エージェント台帳をアプリ設定から取り出し、全ページ共通ヘッダーから開く独立画面にする（決定25）。台帳が持つのは名前・アバター・役割・PM 適格・並び順（優先度）＋特性（T-029）のみとし、担当履歴・担当予定は置かない。アプリ設定側には台帳への導線だけを残す。
  - 受け入れ条件：(1) ヘッダーから台帳の独立画面へ遷移できる。(2) アプリ設定内に台帳の編集 UI が残っていない。(3) 並び順の変更が PM 選出と利用優先度に反映される。

## 自律駆動まわり

自律駆動に関する概念・定義・名前の正本はこの節とする。項目56・57・62・137・141の記述と重なる場合は、この節を優先する。

### 運用の原則

- 自律実行が既定：人の承認を待たずに進める。人の判断が要るものだけが判断待ちに出る。
- プロジェクトの開始・停止が、自律駆動全体の唯一のオン／オフ（2026-11-18 本人決定）。自律駆動が動いていれば、待ち行列から自動で起動するのは当たり前として扱い、そのための個別のスイッチ（旧 Autonomous）は置かない。
- 優先度の決め方：ユーザーが明示的に指定した優先度は固定で最優先し、PM は上書きしない。PM はそれ以外の優先度を主導で変更できる。PM が優先度を変更した場合は、掲示板への報告など、後から追える形に残す。ユーザー指定と衝突する変更が必要な場合は、判断待ちとしてユーザーに上げる。優先度の初期値は、待ち行列に入った順のままとし、自動ルールでは付けない（2026-11-19 項目165で確定：「入った順」の起点は Issue の作成順とし、資格のある課題を作成順に並べる FIFO とする。後から資格ラベルが付いた古い Issue も、作成順の位置に入る）。変更できるのは PM とユーザーだけとする（項目147）。依存関係も PM が制御する：依存で機械的に止める仕組みは作らず、依存待ちは「詰まっている」の理由として扱い、解消の判断と順序付けは PM が行う（項目147）。Issue Monitor は待ち行列の順序どおりに起動するだけとし、順序の決定には関与しない（項目147）。
- 名前について：概念名・画面名・操作名は、本人のインタビューで確定する。umbrella の「自律駆動」は本人の言葉で確定（2026-11-18）。それ以外の名前は、特に断りがなければ仮である。

### 概念の一覧

- **自律駆動**（総称）：プロジェクト単位の、取り込み・起動・監視の自律的な運転の総称。状態は「自律駆動中／停止待ち／停止中」。置き場は、状態と開始・停止がプロジェクト一覧、主要な設定がプロジェクト設定の「自律駆動」の節。
- **Issue Monitor**（仕組み）：自律駆動の実行役で、画面ではない。取り込み・補充・割り当て・起動と、型つきのエスカレーションを担う（項目62）。
- **取り込み**（仕組み）：Open の課題から、取り込み条件に合うものを待ち行列へ入れること。新規の課題だけでなく、Issue の更新の取り込みも含む（現行の事実）。
- **取り込み条件**（設定）：取り込みのフィルター。資格ラベルが付いたもの・除外ラベルでないもの・Open のみ、で決まる。実体は詳細設定に、要約はプロジェクト設定の「自律駆動」の節に置く。
- **待ち行列**（状態）：開始待ちの課題の並び。順序は課題の優先度そのもの。
- **課題の優先度**（属性）：待ち行列の順序。決め方は「運用の原則」のとおり。置き場は課題の一覧・詳細（順序の表示と並び替え）。
- **自動補充**（仕組み）：常時オンで、オン／オフのスイッチは置かない（2026-11-18 本人決定）。資格ラベルが付いた開始待ちの課題を自動で補充する。待ち行列に上限はなく、資格のある課題は全部入れる（項目146）。取り込みの制御はスイッチではなくラベルで行い、自律駆動の開始・停止だけが全体のオン／オフとして残る。
- **補充の上限**（廃止）：待ち行列の上限を無しとしたため廃止した（項目146）。
- **同時実行数**（設定）：同時に動かすエージェントの上限。決め方は2方式とし、自動算出（端末の負荷＝CPU・メモリだけを材料に、負荷を見て随時調整する）が既定で、固定設定で上書きできる。ツールの残量・制限は算出に混ぜない。負荷連動が効くのは同時実行数だけである（項目146）。この上限とは別に、端末全体の同時実行数の上限があり、プロジェクト別の上限はその内訳として扱う（項目207）。自動算出で上限が下がったときは、実行中のセッションは終えるまで待ち、新規起動だけを絞る。例外として、端末が危険域（メモリ枯渇寸前など）に入ったら実行中も止める。線引きは上限の超過数ではなく端末の危険域とする（項目164）。
- **監視**（仕組み）：自律駆動の内訳の1つで、独立したオン／オフは持たない（項目191）。PM の巡回と Issue Monitor の検知で、止まったエージェントの立て直しと判断待ちの運搬を行う。プロジェクトの開始・停止に従う。
- **開始・停止**（操作）：プロジェクト一覧の操作で、自律駆動全体の開始と停止。停止はドレイン方式（新しい割り当てと巡回を即座に止め、動いているエージェントは作業が終わってから止まる。「停止待ち」を経て「停止中」になる。項目56）。確定フローは項目179：停止の確認で即座に停止待ちに入り、停止指示は gwtd が型つき steering としてセッションの入力へ入れる。活動が続いているセッションは終わるまで待ち、活動がスタック判定の時間を超えて途絶えたセッションだけを固着として自動で強制停止する。停止を取り消す操作は無く、停止待ちは再起動を跨いで保持される。
- **再起動後の継続**（設定）：gwt の再起動をまたいで、このプロジェクトが動き続けるか。旧名は「実行ポリシー」。置き場はプロジェクト設定。動き続けるかどうかは自律駆動の状態に従う（停止中なら再起動後も動かない）内訳であり、独立した止める操作は持たない（2026-11-19 項目191で置き換え：従来の「止める操作は『再起動後の継続を止める』で、自律駆動の停止とは別の操作」は廃止）。
- **エージェントの一時停止**（操作／状態）：エージェント単位の一時停止。プロジェクトの停止とは別。置き場はプロジェクトの「エージェント履歴・予定」。
- **プロジェクトを閉じる**（操作）：プロジェクトをこの端末で閉じる。自律駆動の開始・停止とは別の操作。置き場はプロジェクト設定の「閉じる」の節。
- **起動候補**（設定）：課題を始めるときの候補と、その起動条件（セッションの始め方／動かす場所など）。置き場はプロジェクト設定の「作業の進め方」の節。候補の適用順は独立設定ではなく、担当（エージェントの並び順）と実行環境（プロジェクトの優先度）の合成結果とする（項目190）。候補での指定は、その場の上書きとして実行環境の設定より優先される（項目189）。
- **詳細設定の調整値**（設定）：試行上限、スタック判定の無進捗時間、ハートビート間隔、PR マージ監視の上限、Deliver Fix ループの上限、リトライとレビュー。置き場は詳細設定。主要な切替だけを「自律駆動」の節に置き、細かい調整値は詳細設定に分ける（項目57）。（起動を止める使用率の閾値は、項目207により端末全体の設定に置く）

### 止める系の対応（同じ結果に複数の名前を持たせない）

- **自律駆動を止める**：プロジェクト一覧の開始・停止。対象は自律駆動全体。再起動後の継続と PM の監視は、この停止に従う内訳であり、独立した止める操作は持たない（項目191）。
- **エージェントを一時停止する**：対象はエージェント1人（そのエージェントへの新規割り当てだけ）。
- **プロジェクトを閉じる**：対象はプロジェクト自体（この端末で閉じる）。止める操作とは別の、開く・閉じるの操作。

### 競合の扱い

- 占有は「競合を完全に防ぐ」前提で設計しない。キャッシュのタイミングによっては、複数端末で同じ課題を取り合う競合が起こり得る（現行の事実）。
- 引き取り時の占有付けに加えて、起動前に、新鮮な状態で占有を再確認する。
- 競合が検出されたら、後発が降りる：自分の待ち行列から外し、開始したセッションは止める。
- 当面の占有は、資格ラベルが担う（フィルターと占有を兼ねる）。GE によるチーム開発が入れば競合の問題自体が無くなる前提で、この方式は置き換わる。
- 競合の発生は、掲示板への報告など、見える形に残す。

### ラベルの定義（挙動に影響するもの）

ラベルは「隠れたスイッチ」にしない。効果は、課題の行や詳細で属性として見える形にする。設定側（取り込み条件）からも、各ラベルの定義に辿れる形にする。

- **廃止：Hold（gwt-hold）**：取り込みと起動の対象から外す除外ラベルだったが、待ち行列に入れない制御は資格ラベル（付いていない＝入らない）に一本化できるため廃止した（項目148）。
- **資格ラベル**（取り込み条件／占有。名前は仮）：待ち行列に入れる資格を表すラベル。端末のリフィルは、このラベルが付いた課題だけを取り込む。取り込んだ端末がラベルの状態を変えることで、他端末のリフィル対象から外れる（ラベルがフィルターと占有を兼ねる）。GE（チーム開発の通信）が実装された時点で、この方式は置き換わる（当面の方式）。状態を変える実体は、占有を表す状態への付け替えとする。占有した端末が落ちた場合は、ハートビート＋TTL で自動解放する。伝播遅延で2台が同時に取り込んだ場合の検知は起動前の再確認だけとし、後発が降りる（項目175）。
- **除外ラベル**（取り込み条件）：取り込みから外すラベルの指定。
- **gwt-feedback**（担当の振り分け）：フィードバック課題の担当レーンを示すラベル。取り込み条件とは別に効く。
- **gwt-spec**（種別の印）：SPEC の課題であることを示すラベル。設計の進め方（SPEC のワークフロー）に影響する。
- **auto-merge**（PR 側の印）：PR の自動マージの対象であることを示す。課題ではなく PR に効き、著者などの条件と併せて判定する。
- **廃止：許可するラベル**（自律実行がオフのときでも聞かずに始めてよい指定）は、自律実行スイッチの廃止で役割を失ったため廃止した。
