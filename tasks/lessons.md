# Lessons Learned

## L001: 実装前ワークフロー（仕様策定 + TDD）の省略

- **事象**: プランの実装指示を受けた際、CLAUDE.md の実装前ワークフロー（GitHub Issue gwt-spec 作成 → TDD RED 確認）を省略し、直接実装に着手した
- **原因**: プランが詳細だったため、そのまま実装に入れると判断した。CLAUDE.md の必須ワークフローを確認しなかった
- **再発防止策**: feat / fix / refactor の実装開始前に必ず以下を確認する
  1. GitHub Issue (`gwt-spec` ラベル) が存在するか → なければ作成
  2. テストを先に書いて RED を確認 → その後に実装コードを書く
  3. `tasks/todo.md` に Plan・ステップを記録してから着手する

## 2026-03-03 — refactor: ChromaDB コレクション名リネーム

### 事象

`refactor:` タイプのコミット（Python スクリプト内の文字列定数リネーム）を実装した後、
ユーザー確認でGitHub Issue 未作成・TDD テスト未追加の漏れが発覚した。

### 原因

- 変更規模が軽微（1ファイル・8行）だったため、CLAUDE.md の「`refactor:` 対象は
  GitHub Issue を作成してから実装」ルールを省略してしまった。
- Python スクリプト内の定数は Rust ユニットテストから直接検証しにくいと思い込み、
  `include_str!` で埋め込まれた文字列として検証できる手段を見落とした。

### 再発防止策

1. **コミットタイプに関わらず** `feat` / `fix` / `refactor` は必ず実装前に
   `gwt-spec` ラベル付き Issue を作成する。適用除外は `docs:` / `chore:` のみ。
2. Python スクリプトが `include_str!` で埋め込まれている場合、
   定数文字列の存在チェックは Rust の `assert!(SCRIPT.contains("..."))` で書ける。
   「Python だからテストしにくい」は誤り。
3. 計画（Plan）実行時に「仕様策定・TDD は済んでいるか？」を必ずチェックリストで確認してから実装に着手する。

## 2026-08-13: idle agent の process kill → relaunch は復旧にならない

- 事象: 裁定待ち idle の #3526 agent（生きた codex プロセス）を kill → issue.monitor.launch_now で復旧を試みたが、relaunch は「Process exited」で即死し、pane は idle→stopped に劣化。ユーザーのキー入力で起こせる状態を自ら潰した
- 原因: Monitor relaunch は resume 経路を強制（#3548）で、writer lock 解放だけでは resume 成功の十分条件にならない。kill はセッション健全性を壊すだけだった
- 再発防止: 生きた idle セッションは「最も回復可能な状態」であり、プロセス kill を復旧手段にしない。復旧実験は必ず1件だけで検証し、失敗したら他へ展開しない（今回それは守った）。根治は #3548 の FreshRequired fallback を待つ

## 2026-08-15: CI 失敗の所在を単一ブランチだけで断定した

- 事象: PR #3598（#3508）の CI が同一テストで 2 回失敗したため「#3508 の変更が Linux でこのテストを壊している」と判定し、PR を draft に差し戻して担当 agent へ「Linux 環境での再現と修正」を依頼した。その後、無関係な #3466（PR #3486）でも同一テスト・同一エラーが発生し、判定が誤りと判明。真犯人は develop 側に入っていたテスト自体で、#3601 として起票し直した
- 原因: 「2 回連続で再現したから実バグ」までは正しかったが、**所在の切り分けを 1 ブランチの中だけで行った**。#3597（#3480 + develop）が PASS したことを「#3508 固有」の根拠に使ったが、PASS 1 回では develop 側の不安定さを否定できない
- 再発防止: **実バグと判定した後、所在を断定する前に「別ブランチでも起きるか」を確認する。** 特に develop から取り込んだ新しいテストが絡む場合は、他の open PR の CI 結果を見れば追加コストゼロで検証できた。判定の撤回は #3508 にコメントで明示し、draft 差し戻しが過剰だったことも記録した

## 2026-08-15: 選択肢を提示する前に用語の指す範囲を確認しなかった

- 事象: #3466 の AC-1（レイアウト root の扱い）でオーナーに A/B の選択を求めた際、「レイアウト root」を*複数リポジトリを並べた親ディレクトリ*と説明し、「A だと巨大な単一 store に混ざる」と B を推奨した。実際には gwt の Nested Bare + Worktree レイアウト root（= 単一リポジトリの worktree 置き場）を指しており、懸念した事故は起きない。B 裁定を得た後に実装とテスト名を読んで誤りに気づき、訂正コメントを出して再確認待ちになった
- 原因: Issue 本文の AC 文言だけを読み、**実装とテスト名を確認せずに選択肢の説明文を書いた**。`a layout root and its linked worktree resolve to one project store` というテスト名を先に見ていれば、A が既定路線であることも用語の範囲も分かった
- 再発防止: **判断を仰ぐ選択肢を作るときは、必ず実装側の該当箇所（関数名・テスト名・doc comment）を先に読む。** ユーザーの時間を使う質問ほど、前提の裏取りコストを惜しまない。誤った前提で裁定を得ると、訂正 → 再確認で往復が倍になる

## PM 代理でコンフリクト解消してよい境界（2026-08-15）

**事象:** 担当 agent が 18 時間ゼロ稼働のまま、CI 緑だが CONFLICTING の PR が 2 本滞留した（#3577 = #3504、#3589 = #3557）。PM が代理解消を試み、一方は成功・一方は中断した。

**原因:** コンフリクトには「機械的統合で正解が一意に決まるもの」と「実機検証なしには正誤を判定できないもの」がある。両者を区別せず一律に代理解消すると、後者で flaky test や誤った semantic merge を develop に持ち込む。

**再発防止策:**
- **代理解消してよい**: import の union、単一 match arm のシグネチャ変更取り込みなど、**両側の意図が明白で `cargo check` / `clippy` / 対象テストで正しさを機械的に確認できるもの**。#3577 はこれに該当し、fmt/clippy/approval 19・pty_io 8・input_trace 2 の PASS を確認して push → CI 17/17 → マージまで到達した。
- **代理解消しない**: ヘルパー API の刷新と新規テスト追加が衝突したケースなど、**どちらの設計方針を採るかの判断と、実機（Playwright ライブ等）での検証が必要なもの**。#3589 はこれに該当。`git merge --abort` でブランチを無傷に戻し、調査結果（衝突箇所・原因・解消手順・注意点）を Issue コメントに残して担当へ委譲した。
- 中断する場合も**調査結果は必ず残す**。「触らなかった」ではなく「ここまで分かっている」を渡すことで、担当の再開コストを下げられる。
- 代理解消後は `git rev-parse HEAD` と `origin/<branch>` を突き合わせ、ブランチを無傷に戻したことを実測で示す。
